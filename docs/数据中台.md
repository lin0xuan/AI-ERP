# 电商数据中台首版

## 范围与入口

在现有 AI ERP 内增加「数据中台 → 数据工作台」，包括数据接入、主数据、主题数据、指标中心、质量与追溯、数据服务与看板六个页签。

本版从 ERP 已落库的多平台订单、退款、商品明细、自有库存、采购订单采集。平台开放接口鉴权与拉取仍由原 ERP 完成。中台不新建另一套平台连接器，也不会修改订单、退款或库存原表。

这是面向当前单体系统的可用首版：全量对账、分页读取、不可变快照、统一指标服务；尚非实时 CDC、分布式数仓或通用低代码数据开发平台。

## 安装

1. 按根 README 配置现有 MySQL 与应用。启动时默认通过 `erp-api/src/main/resources/db/data-center.sql` 幂等创建 `dc_*` 表。只新增中台表；不自动修改业务表。
2. 如部署账号没有 DDL 权限，由数据库管理员预先执行该 SQL，再配置 `data-center.initialize-schema=false`（环境变量 `DATA_CENTER_INITIALIZE_SCHEMA=false`）。
3. 在目标 ERP 数据库执行 `docs/migrations/20261121_data_center_menu.sql`。脚本可重复执行，只安装三条菜单/权限记录，不自动给普通角色授权。重新登录以刷新菜单。
4. 管理员默认可用。其他角色按需授予 `data:center:read`（读取整个 ERP 数据域）及 `data:center:manage`（全域同步与映射修改）。只管理一个店铺的用户不应获得这两项全域权限；本版不提供按商户/店铺隔离授权。
5. 构建并启动后，在「数据接入」点击「同步并发布快照」。库存里已有规格编码、商品编码的记录会自动对齐。其余编码在「主数据」补齐映射后再次同步，查看质量问题和指标。本次修正只进入新快照，已发布快照保持原结果。

前端执行 `npm run build`；后端执行 `mvn -pl erp-api -am test`。不需要新增模型 API key，数据中台本身不调用模型。

## 数据流与事务

```text
现有平台接口 → ERP 来源表 → 每次按 ID 分页读取（500 行/页）
  → 选定字段快照 → 编码映射 → 质量检测 → 原子发布批次
  → 共用指标服务 → 看板 / HTTP 接口 / AI 工具 / AI 销售分析
```

- 同步采用数据库 REPEATABLE READ 事务，通过 `dc_state` 行锁串行化发布和映射修改。所有源表使用一致性读；成功后一次性切换最新批次。
- 任一源表读取、写入或检查失败，整批事实与质量记录回滚，任务记录 FAILED；旧快照仍可用。失败任务可重新点击同步重试。
- 每次全量对账可反映迟到退款、旧订单修改与源记录硬删除。重复同步不会将同一订单累计多遍。
- 任务状态保存在 `dc_job`，记录开始/结束时间、操作人、行数、质量问题数和映射版本。页面显示最近 50 次任务。首版同步是最长 300 秒的同步请求，界面等待上限330秒；代理需要相应超时配置。网络超时后先刷新任务，避免立即重复提交。进程突然退出可能留下 RUNNING 记录，此时确认进程结束后重新同步；旧快照不受影响。
- 历史快照不自动删除。备份应包含全部 `dc_*` 表；大量数据部署前需设计保留周期和归档策略。本版未完成生产容量验收。

表职责：`dc_state` 发布指针和映射版本；`dc_job` 任务；`dc_fact` 主题快照；`dc_issue` 质量问题；`dc_mapping` 当前映射；`dc_mapping_history` 映射审计历史。

## 主数据

支持商品、SKU、店铺、仓库和供应商统一编码。相同实体的多个来源键可以映射到同一统一编码。手工映射优先。

没有手工映射时，库存直接使用 `sku_code`、`goods_num`。订单明细按这个顺序识别 SKU：手工映射、明细自己的 `sku_code`、`erp_goods_sku_id` 在库存中对应的规格编码、`outer_sku_id`。商品同样优先使用 `erp_goods_id` 对应的 `goods_num`，其次是 `outer_product_id`。同一 ERP SKU 若出现互相冲突的规格编码，不自动合并。仍然无法确定时保留来源键，并记 `UNMAPPED_SKU`。

商品明细和退款都用平台订单号关联订单，键为 `商户ID:店铺ID:平台类型:平台订单号`。明细不再使用内部 `shop_order_id` 作为关联键。

| 类型 | 来源键格式 |
| --- | --- |
| 店铺 | `商户ID:店铺ID` |
| 平台商品 / SKU | `商户ID:店铺ID:平台类型:商品ID或SKU_ID` |
| ERP 商品 / SKU | `erp:商户ID:商品ID或SKU_ID` |
| 仓库 / 供应商 | `商户ID:实体ID` |

映射修改记录版本、操作人和时间。新映射仅在下一次成功同步生效，已经发布的事实不会被追溯覆盖。首版页面最多展示1000条映射，尚无批量导入与模糊匹配。

## 指标口径 payment-cohort-v1

日期时区固定 `Asia/Shanghai`，起止日均包含，服务转为 `[起始日零点,结束日次日零点)`。支持秒级/毫秒级业务时间，异常时间隔离。单次查询最多367个自然日。

| 指标 | 计算 |
| --- | --- |
| 支付金额 | `oms_shop_order.payment_amount`，单位分，按 `pay_time` 筛选。状态 21 不计入。状态 0、11、13、22、29 且支付时间为空或 0，视为未支付，不计入，也不记质量错误。这些状态若已有支付时间则保留。待发货、已发货、已完成等状态缺少支付时间仍隔离 |
| 成功退款 | 同批次中 `refund_status=3` 的退款，按商户+店铺+平台类型+原订单号关联筛选支付期订单；不按退款申请时间筛选 |
| 净销售额（支付批次） | 支付金额减该批订单截至快照的成功退款；不是退款发生期现金流，也不是财务确认收入 |
| 快照可用库存 | `o_goods_inventory.available_quantity`，排除已删除/隔离行；是同步时点快照，不随支付日期变化 |
| 采购订单金额 | `erp_purchase_order.order_amount` 由元精确转换为分，按 `order_time` 统计，排除状态99；不是付款额或销售成本 |

已经付款但随后取消/关闭的订单保留支付事实，通过成功退款冲减，不能一边剔除订单一边重复扣退款。运费和税费遵循源支付字段定义，不额外扣减。所有金额计算使用整数分或 BigDecimal，不用浮点求和。

币种为人民币。Amazon(800)、Shopify(850) 来源因缺失统一币种/汇率数据，首版自动隔离，不混入人民币指标；其他来源须确保入库金额为人民币。本版不计算毛利、库存周转率或外币折算，现有来源不足以支持可靠成本/期间平均库存口径。

看板、`getDataCenterMetrics` 和 AI 销售分析复用 `DataCenterService.metrics`。AI 销售分析默认近7个北京时间自然日；聊天可指定日期、统一店铺编码及批次。固定同一 `batch` 和过滤条件才能与历史看板精确比对。模型生成文字仍需人工判断，但工具返回的数字与看板来源一致。

## 质量与追溯

- `INVALID_VALUE`：缺失身份、关键字段、异常时间、负金额/数量及未支持币种；ERROR，隔离。无支付时间的未支付订单不走这条规则。
- `DUPLICATE_KEY`：订单、退款、采购业务键重复；全部重复行隔离，不任取一条。
- `ORPHAN_REFUND`：成功退款不能匹配有效支付订单；ERROR，不冲减指标。
- `UNMAPPED_SKU`：商品明细没有手工映射、规格编码、ERP SKU 或外部编码；WARN，保留来源编码。
- `MISSING_ORDER_NO`：商品明细没有平台订单号；WARN，不关联订单。
- `ORPHAN_ITEM`：平台订单号在本快照中没有订单；WARN。明细不参与金额指标。
- `STOCK_BALANCE`：库存数量关系不平；WARN。
- `REFUND_EXCEEDS_PAYMENT`：成功退款超过订单实付；WARN，保留负净额供核查，不静默截为0。

追溯接口返回来源表、原始ID、批次、选定来源字段、标准化事实和质量问题。明细和退款附带父订单，订单附带同一平台订单号下的退款和明细。只复制经营分析必要字段，不复制收件人姓名、电话、地址、平台 token 或模型凭据。修正原始数据/映射后重新同步；历史问题保持可查。

## 接口

统一前缀 `/api/erp-api/data-center`，使用现有登录态。

| 方法 / 路径 | 用途 | 权限 |
| --- | --- | --- |
| GET `/catalog` | 来源、指标字典、版本 | read |
| GET `/jobs` | 最近同步任务 | read |
| POST `/sync` | 执行并发布快照，失败返回 FAILED 任务 | manage |
| GET / PUT `/mappings` | 列表 / 保存映射 | read / manage |
| GET `/metrics?from=2026-11-01&to=2026-11-21&shop=1:1&batch=...` | 统一经营指标；shop/batch可省略 | read |
| GET `/rows?kind=order&page=1&size=20&issues=false&batch=...` | 主题/质量分页，size最大100 | read |
| GET `/lineage?kind=order&id=1&batch=...` | 来源与问题追溯 | read |

## 验证与复现

- 数据中台测试：`mvn -pl erp-api -am test -Dtest=DataCenterServiceTest -Dsurefire.failIfNoSpecifiedTests=false`，默认内存 H2 MySQL 模式，不访问真实业务库。
- 同一组测试可使用独立 MySQL：设置 `DATA_CENTER_TEST_JDBC_URL=jdbc:mysql://127.0.0.1:13316/datacenter_test?useSSL=false&allowPublicKeyRetrieval=true`。仅允许本地 `datacenter_test*` 库，使用隔离测试实例 root 空密码；每个测试会重建该库中的测试表，禁止指向业务库。
- 页面夹具：前端启动后打开 `/tests/data-center-ui.html`。所有请求使用合成数据，支持映射保存、同步切换、主题/质量查询、追溯抽屉、指标看板。截图 `docs/images/data-center-fixture.jpg` 是该夹具，不是生产经营数据。
- 本轮已完成后端测试、新增13项用例的 H2 与独立 MySQL 8.4 回归（包括2001笔订单完整汇总）、仓库五张源表 DDL 字段契约核对、菜单脚本两次执行幂等验证、Vue 类型检查及生产构建、六个页签的浏览器操作检查。
- 页面夹具在切换表格/抽屉时出现 `ResizeObserver loop completed with undelivered notifications` 通知；本轮映射保存、同步发布、追溯与看板操作均完成，未对该通知作专门修复。前端构建保留项目现有的大包体和重复导入提示。
- 未执行真实电商平台拉取、付费模型回答验收、真实业务库迁移、生产部署与容量压测。原有记忆 MySQL 集成测试因未配置专用环境跳过，不算通过。
